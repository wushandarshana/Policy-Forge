## What was built
The renewal backend: V10, the current paid term, the cycle, the scheduler, the admin job, the pay endpoint and the detail additions. No rule file and no spec file was touched.

- **V10 (C8).** `V10__policy_term_rule_version.sql` adds `policy_term.rule_version`, backfills it from each policy's version 1 and makes it NOT NULL (with a `>= 1` check). V1 to V9 are byte-identical to `12f95c3` (checked with `git diff`). `PolicyTermEntity.of(..., paid, ruleVersion)` sets the rule version at construction (no setter), issuance writes term 1 with the quote's rule version, and `markPaid()` refuses an already-paid term (`IllegalStateException`).
- **Current paid term (G-5).** `service/PolicyTerms` maps the stored terms onto the TASK-001 `RenewalPolicy` and is used by `PolicyQueryService` (header, C2 summary, C3), `EndorsementService` (window, basis, preview) and `RenewalService`. An unpaid offer changes nothing; a paid renewal term is current from the moment it is paid. The detail gains `terms[].ruleVersion` and `pendingRenewal` (`{termNo, startDate, endDate, premium, ruleVersion, payableUntil}` or null; `payableUntil` = current paid term end + the grace days of that term's own rule version).
- **Cycle (P-7).** `RenewalService.runCycle` takes every in-force policy ascending by number and processes each in its own `TransactionTemplate` transaction: offer (premium from `PremiumCalculator` over the current version's stored risk inputs, with the rule version active on the run date, which the term records; dates from `RenewalPolicy.renewalDates`), then lapse through `PolicyEntity.applyTransition` (so `PolicyStateMachine` decides) with reason `GRACE_PERIOD_EXPIRED` and actor `system:renewal-scheduler`, even for an admin run. A policy whose offer window was missed is offered and lapsed in the same run. A lost race (unique term key, optimistic lock) or any other failure skips that policy only, and is logged by policy number. Each run appends one `RENEWAL_CYCLE_RUN` audit entry (entity type `RENEWAL_CYCLE`, entity id the run date, actor the admin or `system:renewal-scheduler`).
- **Scheduler.** `RenewalScheduler.runScheduled()` carries `@Scheduled(cron = "0 0 23 * * *", zone = "${policyforge.time-zone:Asia/Kolkata}")`, runs for today on the injected clock and holds no logic. `config/SchedulingConfig` has `@EnableScheduling` behind `policyforge.scheduling.enabled` (default on); the new `src/test/resources/application.properties` sets it to false, so no trigger exists in any test context.
- **C1.** `POST /api/admin/jobs/renewal-cycle?date=` (`AdminJobController`): ADMIN, `consumes` JSON only, body empty or `{}`; unknown keys (sanitised) and a malformed `date` are reported together as 400; 200 `{runDate, offersCreated, lapsed}`.
- **C2.** `POST /api/policies/{n}/renewal/pay` (`RenewalController`): CUSTOMER owner, JSON only, body empty or `{}`. P-5 order: 400 body keys, 404 lookup/owner, 409 invalid-policy-state (state machine refuses RENEWED), 409 `NO_PENDING_RENEWAL`, 409 `RENEWAL_PAYMENT_WINDOW_CLOSED`. One transaction marks the term paid, appends version n+1 (the current version's inputs, sum insured, address and nominees with the renewal term's premium, rule version and dates) and moves the policy to RENEWED with reason `RENEWAL_PAID`, actor the owner. A race loser gets 409 `POLICY_UPDATE_CONFLICT` and writes nothing. Response 200 `{policy, term}`.
- New conflict codes in `ConflictException` and fixed details in `GlobalExceptionHandler`. `EndorsementService.isUniqueViolation` moved to the shared `WriteConflicts`.

## Open issues
- **For TASK-007 (E2E).** Both endpoints consume `application/json` only, even with no body. A Playwright `request.post` with no `data` sends no content type and gets 415, so call the job and the pay with `data: {}` (a JSON content type). The job's `date` is the query parameter (`?date=YYYY-MM-DD`).
- **`pendingRenewal` on a policy that is not in force.** The API returns `null` for LAPSED and CANCELLED, because that offer can no longer be paid; the unpaid term stays in `terms[]`. For an in-force policy it is non-null from the offer until it is paid, including after `payableUntil` (the SPA then gets the 409 `RENEWAL_PAYMENT_WINDOW_CLOSED` on Pay, which TASK-002 already handles). Say so if the evaluator reads C5 as "also non-null when lapsed".
- **Test seeding (P-15, TASK-006).** The renewal ITs share one context of their own (marker property `policyforge.test.context=renewal`) because the job lapses every in-force policy it finds. They assert their own policy numbers (`contains`, never exact lists), except the two idempotency checks, which hold with any seed. When TASK-006 adds the seed to every context, those assertions stay valid; the seed's own AC-11.1 context must not run the cycle with a later date than the seed expects.
- **Unreached branches (no test fixture).** A policy the active rule version rejects (SG-7) and a run date with no active rule version both skip the offer with a warning by policy number. They are covered by code review and the isolation test's skip path, not by a dedicated test.
